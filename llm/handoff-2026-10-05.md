# Hand-off to backend — 2026-10-05

New Gantt/INFO rendering requirements came in (reference doc + a real Excel
screenshot showing the expected Gantt layout). The `llm` branch side (schemas +
prompts) is done and pushed (`86db705`); this note is the backend checklist to
make the running app actually reflect it. None of this is live-tested yet — see
"Needs a live-run test" at the bottom.

## 1. Merge `llm` → `backend`

Pull in `llm/schemas/*.json`, `llm/prompts/*.request.json`, `llm/examples/*`.

## 2. Update the Zod schemas (backend's mirror of `llm/schemas/*.json`)

**`info.schema.json` — breaking changes:**
- Removed: `roles`, `website`, `socialMedia`, `repository`, `mailingLists`. Drop
  these from the Zod schema and from the INFO Word template (those sections
  should no longer exist in the rendered document at all, per the notes doc).
- Added, both required with numeric defaults (never `"tbd"` — these are numbers):
  - `ownEntityTotalPersonMonths: number` (top-level)
  - `workPackages[].ownEntityPersonMonths: number`
  - `workPackages[].tasks[].participants: string[]` (required array; may be `["ALL"]`
    or a list of short names; empty array if the source task had no "Partners
    involved" annotation at all)

**`gantt.schema.json` — no type change, behavior change only:**
- `deliverables[].taskId` was already optional/present — no Zod change needed —
  but the *rate* at which the LLM sets it is expected to jump way up (previously
  ~5/50 deliverables in the one large GA tested; now expected close to 100% of
  deliverables whose WP has tasks at all). Mention this if you had any downstream
  logic assuming `taskId` is usually absent.

## 3. Render engine changes (the actual visible-to-user work)

**Gantt Overview sheet:**
- Deliverables render **only** on their `taskId`'s task row (never the WP row).
  Milestones render **only** on the WP row (already true via
  `workPackages[].milestoneIds` — unchanged).
- WP rows get a visibly darker background than task rows (reference screenshot:
  medium gray WP rows vs. near-white task rows).
- Deliverable cell color = `disseminationLevel` (green = `PU`, amber/orange =
  `SEN` — see legend in the reference screenshot, top-left "D=DELIVERABLE").
- Year header band: "Year 1" style labels get the calendar year appended, e.g.
  `"YEAR 1 - 2024/2025"` — derive from `projectStartDate` + `totalMonths`, not
  from any new field (we already send `projectStartDate`).
- Month header: `"M1 - OCT"` style — same, computed, no new field.
- Reporting Period boundary: vertical border between the last month of each
  `reportingPeriods[]` entry and the first month of the next, with a centered
  `"REPORTING PERIOD N"` label spanning that period's columns (see reference
  screenshot — it's a background label across the empty task-row area, not a
  per-cell value).

**Deliverables List / Milestones List sheets:**
- "Due Date" column: prefix the month number with `"M"` (`dueMonth: 12` → cell
  text `"M12"`). Pure formatting; `dueMonth` stays numeric in the JSON.

**INFO Word doc:**
- Duration: render as `"{duration.totalMonths} Months"` (e.g. `"24 Months"`),
  not `"{duration.totalMonths}M"`.
- Delete the Website / Social Media / Repository / Mailing Lists paragraphs
  from the template (data no longer exists to fill them).
- Delete the Roles section/table from the template.
- New "VIL Efforts" section, hierarchical:
  1. `ownEntityTotalPersonMonths` (one line)
  2. Per WP: `workPackages[].name` + `workPackages[].ownEntityPersonMonths`,
     with a blank line between WPs
  3. Per task within a WP (where applicable): task name + effort context
- **Every** WP and task from `workPackages[]` must appear (not filtered to
  ownEntity) — bold only the ones where ownEntity is involved: a WP/task is
  "ownEntity-involved" if `leadBeneficiary`/`leader` equals ownEntity's short
  name, **or** `tasks[].participants` contains ownEntity's short name or the
  literal `"ALL"`. A WP counts as involved if it's involved itself or any of
  its tasks are.

## 4. Templates (`docs/templates/`)

The INFO `.docx` template likely still has placeholder paragraphs for the
removed Website/Social Media/Repository/Mailing Lists/Roles sections — these
need to be deleted from the template file itself, not just left empty.

## 5. Needs a live-run test before trusting this

Unlike the `gantt`/`info`/`kpi` extraction rules already validated against two
real GAs (see `llm/testing-notes.md`), these specific new fields
(`ownEntityPersonMonths`, `participants`, the much-higher-rate `taskId`) have
only been validated against one **hand-built** example
(`llm/examples/info.example.md`, `llm/examples/gantt.example.md`), not a live
Anthropic API call. Recommend re-running the same two-GA live test and adding
the result to `llm/testing-notes.md`, the same way the first two rounds were
documented, before shipping this to users.
